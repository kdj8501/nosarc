# Nos Arc 실행 계획

## 1단계: 기반 기능

완료 기준은 다음과 같다.

- 웹 서버가 `.env`에서 비밀번호를 읽고 세션을 발급한다.
- 비밀번호 화면에서 `assets/uma.gif`가 정상적으로 로드된다.
- 작품 생성, 장르 태그 연결, 화 번호 등록이 가능하다.
- JPG·PNG·WEBP·PDF·CBZ 업로드가 가능하다.
- 원본 파일과 표준화된 페이지 이미지가 분리 저장된다.
- 서재와 화 목록에서 번역 상태를 볼 수 있다.

## 2단계: 비동기 처리

- Redis 기반 작업 큐와 worker 프로세스를 추가한다.
- `queued`, `preparing`, `ocr`, `translating`, `rendering`, `completed`, `failed`, `cancelled` 상태를 저장한다.
- 작업 상세 API와 전역 진행 패널을 만든다.
- 브라우저를 닫고 다시 열어도 작업이 이어지는지 검증한다.
- 실패한 단계부터 재시도하고, 원본은 항상 보존되는지 검증한다.

## 3단계: OCR과 번역

- 20~100페이지의 대표 샘플을 일본어 세로쓰기, 가로쓰기, 후리가나, 효과음, 저해상도 페이지로 구성한다.
- Manga OCR, PaddleOCR fallback, 번역 후보를 같은 샘플로 비교한다.
- OCR 블록 좌표와 신뢰도를 저장한다.
- 일본어→한국어 결과와 작품별 용어 사전을 저장한다.
- 모델 버전과 실행 설정을 Job에 기록해 결과를 재현할 수 있게 한다.

## 4단계: 리더 품질

- 세로 읽기 순서와 페이지 이동을 검증한다.
- 원본·번역 오버레이 전환을 추가한다.
- 번역이 없는 페이지도 즉시 읽을 수 있게 한다.
- 낮은 OCR 신뢰도 영역을 관리자에게 표시한다.
- SSE 또는 짧은 폴링으로 작업 완료를 자동 반영한다.

## 5단계: 운영 안정화

- N100에서 한 화 50페이지, 100페이지, 300페이지 처리 시간을 측정한다.
- OCR과 번역 단계별 최대 메모리 사용량을 측정한다.
- 모델 캐시와 원본 저장소를 별도 백업한다.
- SQLite 무결성 검사와 미완료 Job 복구를 정기적으로 실행한다.
- 지원 포맷별 샘플과 깨진 파일을 포함한 회귀 검증을 만든다.

## 배포 기준

```text
web       : HTTP 요청, 인증, 서재, 리더
worker    : 작업 큐 소비, AI 단계 실행, 동시성 1
redis     : 작업 큐와 진행 이벤트
data      : SQLite, 원본, 페이지, 썸네일, 모델 캐시
```

운영 배포에서는 리버스 프록시 뒤에 웹 서버를 두고 HTTPS를 사용한다. 미디어 파일도 애플리케이션의 인증을 거쳐야 하므로 정적 서버가 저장 디렉터리를 그대로 공개하지 않게 한다.

## 벤치마크 체크리스트

- 1페이지 OCR, 50페이지 OCR, 100페이지 OCR
- 1페이지 번역, 50페이지 번역, 100페이지 번역
- 모델 최초 로드 시간과 캐시 후 로드 시간
- 작업 중 웹 응답 지연
- 최대 RSS와 디스크 사용량
- 작업 중 프로세스 종료 후 재시작 복구
- 잘못된 PDF, ZIP 폭탄, 암호화 압축 파일, 손상 이미지 처리

초기 합격 기준은 절대적인 페이지당 초가 아니라 서비스 안정성이다. 사용자가 작업 화면을 계속 열어 둘 필요가 없고, 작업이 오래 걸려도 원본 열람과 다른 서재 기능이 막히지 않으면 MVP 요구를 충족한다. 실제 수치는 첫 벤치마크 결과로 문서에 갱신한다.

## 결정이 필요한 항목

- 기본 번역 결과를 오버레이로만 제공할지, 추후 인페인팅 이미지도 저장할지
- 관리자와 일반 열람자를 분리할지, 당분간 공유 비밀번호 하나로 유지할지
- CBR 처리를 서버에 포함할지, CBZ 변환을 업로드 전제 조건으로 둘지
- 외부 번역 API를 허용할지, 모든 원문을 로컬에 남길지
- 장기 보관을 위해 SQLite를 PostgreSQL로 전환할 시점
